Reviewed master baseline `95d94a1` through integrated `e5d5ef5` in the isolated review worktree. Findings below are confirmed by tracing the changed code and installed Sequelize 6.37.8 behavior. Existing tests were run without changes.

## P1 findings

1. **Rollback trusts configured names as proof of ownership** — `packages/sequelize-guard/src/migrations/guard-migrations.ts:161–166`. The new custom table names allow a rollback to resolve an existing application table. `validateGuardTables` prevents duplicate names and protects the particular supplied UserModel. The other prechecks validate search-path and legacy suffix collisions. None establishes that every existing target belongs to Guard before issuing any drop. This matters when rolling back a failed, misconfigured `up`, since `up` refuses existing tables, but `down` will drop the same resolved targets. Require trustworthy migration ownership metadata/receipt or, at minimum, preflight every existing table's expected Guard structure before dropping any table. Missing tables must stay retryable. Add a regression that confirms an unexpected table rejects the rollback before any drop call.
2. **MySQL cleanup can drop a table another migration created** — `packages/sequelize-guard/src/migrations/guard-migrations.ts:104–135,78–80`. Sequelize's installed MySQL generator uses `CREATE TABLE IF NOT EXISTS` (`node_modules/sequelize/lib/dialects/mysql/query-generator.js:130`). Two operations can pass the preflight before one creates a table. The second operation records a successful no-op as its own creation. A later index error or competing DDL then reaches cleanup, which can drop a table owned by the successful migration. Make creation exclusive and only record actual ownership for cleanup. Coordinate migration operations for a namespace if retries must be serialized. Verify on MySQL with a regression that asserts a successful runner's tables persist across a losing runner's cleanup.
3. **Copied legacy role names can retain grants while administration silently misses them** — `packages/sequelize-guard/src/migrations/guard-upgrade.ts:133–144`, `packages/sequelize-guard/src/guard/Roles.ts:343–348,423–435`. Baseline role creation lowercased without trimming. Upgrade copies those stored names without canonicalization. Current role lookup and mutation normalize inputs by trimming and then filter returned rows for exact name matches. Permission authorization evaluates existing linked grants regardless of the old role name. As a result, an accepted legacy role name with edge whitespace can keep its existing grants while permission and membership revocation or role deletion find no target. Normalize on upgrade only after preflighting the entire role set for blank/colliding canonical names and accounting for database collation. Alternatively reject noncanonical roles before destination creation and give an explicit remediation path. Test one unambiguous legacy name and one canonical collision using the published fixture. Warn users that old tables need offline upgrade and verification before serving requests.

## Focused remediation review

Reviewed `342271f` as integrated in `b592f15` at `c7c8843`. The original and integrated patches have matching stable patch IDs. Node 22.17.1 passed all 28 tests in `migrations.test.ts` and `init.test.ts`.

- **Original finding 1, partly resolved.** `guard-migrations.ts:174–180` awaits verification of all existing targets before issuing the first DROP. The new tests prove a shape mismatch preserves all existing tables, missing targets stay retryable, and a SQLite application reference blocks rollback and preserves its rows. Two remaining paths need disposition.
  - **P1. A coincidental shape can still lead to unrelated table loss.** `guard-migration-ownership.ts:42–53,93,129–145` treats passing schema checks as ownership. With default timestamps off, the built-in user table has only an integer primary key named `id` (`GuardUser.ts:93–103`), with no required foreign key or named index. An existing application table with that common shape can pass as the configured built-in user target even if every other Guard table is missing. This also makes a rollback after a failed `up` unsafe if `up` rejected the existing table. Require migration-created ownership metadata or a receipt bound to the namespace and exact target names. Preserve that evidence until the last successful drop so partial retries remain possible. Add a same-shape application-table preservation check.
  - **P2. MySQL rollback can still partially destroy Guard policy before detecting an external FK.** `guard-migration-ownership.ts:146–169` preflights incoming references only for SQLite. MySQL implicitly commits DROP operations (`guard-migrations.ts:75–80,179–180`). An inbound application FK to a later table can reject that DROP after earlier policy tables have been removed. Check MySQL inbound references in metadata before any DROP, including visible referencing schemas, and verify a blocked rollback preserves the full Guard schema and its data.
- **Original finding 2, resolved for competing creates.** `guard-table-ddl.ts:63–74` executes plain MySQL CREATE and fails if the expected generated statement changes. `guard-migrations.ts` records cleanup ownership only after that exclusive create succeeds. The dialect regression coordinates two connections, verifies the winner's existing data is preserved and checks final migration completion. It was reviewed in source. B ran it on MySQL.
- **Original finding 3, resolved for the supported offline upgrade.** `guard-upgrade.ts:111–117,166–188` validates the entire legacy role set before destination DDL, detects canonical collisions and rejects noncanonical names with remediation. Both published 6.0.2 fixture tests passed and assert source rows stay unchanged and destination creation is never called. Carry offline upgrade instructions into the docs. F owns behavior for previously inert parent relationships and invalid persisted names in live authorization.
