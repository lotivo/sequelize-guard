Use deployment migrations to prepare production tables before application workers start. Automatic synchronization is useful for a new disposable database; an existing installation needs a reviewed migration.

## Choose the setup path

| Situation | Use |
| --- | --- |
| New disposable development database | Construct Guard and await `guard.ready`. |
| Explicit setup of a disposable database | Set `sync: false`, then await `guard.sync()`. |
| New production installation | Run `migration.up()`, then start workers with `sync: false`. |
| Existing Guard schema | Follow the matching [upgrade guide](/docs/migration). |

**Do not use `force` or `alter` to upgrade production data.** Explicit `guard.sync()` forwards those options to a supplied `UserModel`, so they can affect application user data as well as Guard tables. Registered holder models are never synced or dropped by Guard.

## Share the schema options

Use the same table names, user model, timestamps and holder registrations in migrations and application startup. This minimal example uses Guard's built-in user:

```typescript filename="guard-options.ts"
import type { GuardOptions } from 'sequelize-guard';

export const guardOptions: GuardOptions = {
  prefix: 'app_guard_',
  sync: false,
};
```

For a custom user or registered holders, initialize those model classes on the migration's Sequelize connection and include them in these options. Apply your application's table migrations first. Static Guard migrations do not own supplied user or holder tables.

## Run the deployment migration

Import your configured connection and options, then run this once through your migration runner:

```typescript filename="create-guard-tables.ts"
import { migration } from 'sequelize-guard';
import { sequelize } from './database.js';
import { guardOptions } from './guard-options.js';

await migration.up(sequelize.getQueryInterface(), sequelize, guardOptions);
```

The order is:

1. Create or migrate application tables.
2. Create Guard tables and associations with `migration.up()`.
3. Start application workers.

Do not call fresh `up()` over a legacy namespace. Use a distinct destination and the [offline upgrade procedure](/docs/migration/upgrade-to-v6-1).

## Start the application

```typescript filename="guard.ts"
import { SequelizeGuard } from 'sequelize-guard';
import { sequelize } from './database.js';
import { guardOptions } from './guard-options.js';

export const guard = new SequelizeGuard(sequelize, guardOptions);
await guard.ready;
```

With `sync: false`, construction and `ready` perform **no database work**. They do not verify that deployment migrations ran successfully. Complete migrations before serving requests, and handle database failures without allowing protected operations.

For a disposable database where you want explicit provisioning, call `await guard.sync()` instead. Await that call itself: `ready` only represents the constructor's automatic startup. A failed setup can be retried with another explicit `sync()` after correcting the cause.

## Roll back a fresh installation

Your migration runner can call:

```typescript
await migration.down(sequelize.getQueryInterface(), sequelize, guardOptions);
```

This drops verified Guard-owned tables, including the built-in user table when configured. It preserves supplied application user and holder tables and refuses mismatched ownership or external application references. Back up data and review dependencies before running it.

MySQL DDL can commit before a migration finishes; interrupted creation or rollback may need manual recovery. Read the [upgrade and recovery guide](/docs/migration/upgrade-to-v6-1) before attempting cleanup.

## Try the complete example

The [runnable migration example](/docs/examples/basic#prepare-tables-with-migrations) creates a disposable database, prepares tables, checks access and rolls back. Your application owns the Sequelize connection and closes it when finished.

For permission statements, use `guard.init().allow(...).to(...).on(...).commit()`. That [fluent builder](/docs/guide/permissions#grant-access-through-a-role) changes policy, not database structure.
