## Authorization reads current database state

`user.can()`, `user.cant()`, role checks, and their corresponding `guard` methods read from the database on each call. `guard.getUserRoles(user)` also reads current membership. Permission checks load membership and permissions together in one query. These reads use Sequelize's writer connection (`useMaster: true`) so a read replica's lag cannot preserve a revoked grant.

After a revocation has committed, a check started outside an older transaction snapshot observes it on every guard instance connected to that database. No process-local cache reset or TTL expiry is required. Database errors reject the check; the library never substitutes a previous allow result. Applications must handle rejection by preventing the protected operation.

```typescript
await guard.ready;
await guard.allow('reader', 'read', 'document');
const user = await guard.makeUser();
await user.assignRole('reader');

await user.can('read document'); // true
await user.rmAssignedRoles(['reader']);
await user.can('read document'); // false
await user.isA('reader'); // false
```

The same behavior applies when another worker removes the membership or permission, or when Sequelize writes update the association tables directly. Deleting a role causes subsequent authorization checks to deny its permissions.

## Consistency boundaries

A check already reading before a revocation commits can still return the earlier result. That result is not saved for later checks. Authorization and the subsequent application operation are not one atomic transaction: applications requiring that guarantee must coordinate both with their database transaction and locking strategy. An existing transaction snapshot can retain older data according to its isolation level.

Permission removal currently matches the complete action bundle originally granted. For example, remove `['read', 'edit']` together if they were granted together for a resource. Removing only `'edit'` from that bundle is a separate known limitation; do not assume it succeeded. Check `permsRemoved` and the resulting authorization. Action-level removal semantics are tracked in the maintenance plan.

## Compatibility with existing cache configuration

`userCache` remains accepted for compatibility but is deprecated: it no longer caches user membership or authorization, whether it is `true` or `false`. `userCacheTtl` controls entries that callers manually place in `guard.getUserCache()`; it does not delay revocation. There is no supported nested `cache: { enabled, ttl }` option.

The existing `getCache()`, `resetCache()`, `getUserCache()` and `resetUserCache()` APIs remain available. The role/permission cache still supports legacy administrative lookups and event snapshots. `resetCache()` clears the snapshot; the next awaited `getCache()` reloads it from the writer connection. Concurrent readers share initialization, failed loads reject and can be retried, and `sync()` reloads the snapshot after synchronizing tables. These snapshots can still be stale across workers or concurrent policy writes. Do not use them, `getRole()` or `allRoles()` as authorization decisions. Use the authorization methods above.

Cached roles retain their Sequelize model identity within a guard instance. Treat objects returned from the administrative cache as read-only; mutating them can change later cached lookups until the snapshot is refreshed.

## Performance

Each authorization call now requires a database read. This trades the old cache-only performance for current revocation behavior. Measure database latency and load before increasing traffic. Avoid caching the resulting boolean in application code unless the application explicitly accepts the resulting revocation delay.

The application still owns authentication and authorization of role/permission administration. Use a principal established by verified authentication; do not treat a user ID from an unverified request header as proof of identity.
