title: Authorization and security
description: Learn how to check permissions and control access in your application.
icon: ShieldCheck
---

Authentication belongs to your application. Resolve the actor from a verified session or credential verifier, then map that trusted principal to a persisted user or registered holder. Never authenticate an arbitrary `x-user-id`, body ID, query ID or unsigned JWT claim. Keep acting identity and target identity separate. Protect every policy mutation with dedicated administrative authorization, validate input and enforce tenant/object scope. Cookie-authenticated writes also require application CSRF protection.

Return 401 for absent/invalid identity, 403 for authenticated denial, and a sanitized 5xx for identity/database failures; never execute the protected action on those paths. Authorization database failures reject rather than returning a policy denial. Follow the [executable HTTP integration](https://github.com/lotivo/sequelize-guard/blob/master/examples/authorization.mjs), including its injected verified-session dependency and real Guard tests.

Wildcards are broad privileges: grant them only deliberately. Permissions are allow-only; the deprecated stored `allow` field does not implement deny rules. Soft-deleted users/holders lose access. Add application object/tenant checks where coarse role permissions are insufficient.

Authorization reads current writer-backed database state and never trusts the manual cache. A check already in flight or an older database transaction can see earlier state. A successful check and a subsequent business operation are not automatically atomic. Plan writer capacity and coordinate business consistency explicitly. Events are best-effort in-process notifications, not durable audit records. Applications own durable committed audit history and persisted expiry enforcement; timers do not provide reliable privilege expiration across restarts/workers.

[Report vulnerabilities privately](https://github.com/lotivo/sequelize-guard/security/advisories/new), with package/Node/Sequelize/dialect versions and a private minimal reproduction. Exclude secrets and customer data. See [SECURITY.md](https://github.com/lotivo/sequelize-guard/blob/master/SECURITY.md) for release support and dependency exposure limits.

Use exact action/resource tokens, for example `await user.can('read article')`. Checks accept exactly two whitespace-separated tokens (outer whitespace is trimmed), or `'*'` for `'* *'`. Tokens are case-sensitive, nonempty and contain no whitespace, NUL, lone surrogate or embedded `*`; wildcard `*` must be the entire token. Thus `read article extra`, `read:article` and `r* article` deny. Creation rejects malformed inputs; malformed stored grants are ignored. Equivalent action sets are deduplicated/canonicalized. Do not reuse a supplied permission name for an incompatible definition.

`await guard.allow('reader', ['read', 'edit'], 'article')` grants permissions through a role. `createPerms(resources, actions)` creates permission definitions without assigning access. `await guard.rmPermsFromRole('reader', 'edit', 'article')` removes that exact action while retaining `read`, without changing unrelated roles. Removing an action from a wildcard grant does not invent an exception/deny rule.

`createPerms` and `createPermsBulk` return models by default and plain data with `{ json:true }`. `makeRoles` returns plain data when options are omitted/undefined; explicit `{}` or `{ json:false }` returns models. `getRole` returns a model or null; `allRoles`/`findRoles` return models. `getUserRoles`/`getHolderRoles` return plain active direct-role data; `user.roles()` returns active direct-role models without join payload.

Mutations accept `{ transaction }` where their declarations expose `PolicyMutationOptions`. Guard-owned operations commit atomically and emit events only after successful commit. Caller-owned transactions use an operation savepoint and suppress built-in events, including after the caller commits. Authorization checks do not accept a caller transaction option. Never interpret event delivery as durable auditing. Event registration returns an unsubscribe function; listener failures may warn after the write has committed.

`safeGuardDeletes:true` (default) makes `deleteRoles` reject roles with permission links, user/holder memberships (including archived links), or child roles. With it disabled, role deletion removes membership/permission links and detaches children before deleting the role; this must be an intentional administrative action.
