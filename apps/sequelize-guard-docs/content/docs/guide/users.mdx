---
title: Users and registered holders
---

Supply an initialized Sequelize model on the same connection using `UserModel`, with one supported primary key (integer, string or UUID). `userPk` names its primary-key attribute or physical column. Composite/unsupported identities are rejected before DDL. Constructor inference preserves mandatory application fields: use `guard.models().GuardUser.create(values)`; `makeUser()` supplies no required fields. See the [strict executable custom-user recipe](https://github.com/lotivo/sequelize-guard/blob/master/examples/custom-user.ts).

Use `assignRole(user, role)`, `assignRoles(user, roles)`, `rmAssignedRoles(user, roles)`, `assignRolesToUsers(users, roles)`, or `assignUserRoles([{ user, roles }])`. Bulk operations are atomic, deduplicate input and return `{ assigned }`, counting new active memberships. Explicit reassign/regrant reactivates archived links. Users must be persisted instances of the configured model.

Register other application models at construction with `roleHolders: { team: Team }`. Type keys start with a lower-case ASCII letter and contain lower-case ASCII letters, digits or underscores. Each model gets a separate typed junction with a real FK; identical IDs in different models do not share grants. Use `assignRolesToHolder(team, ['reader'])`, `holderCan(team, 'read article')`, `getHolderRoles(team)`, and `removeRolesFromHolder(team, ['reader'])`. Permissions remain attached to roles, not directly to arbitrary holders. Application migrations create holder tables before Guard migrations. `migration.addRoleHolders(queryInterface, sequelize, options)` adds new junctions to an existing owned schema. Its `roleHolders` option must contain **only newly added registrations**; repeating an existing type is rejected. Keep all other schema options matched to the existing installation. Run this migration before starting a new application Guard. The subsequent constructor, `migration.down`, and `migration.upgrade` configurations must contain the **complete set of registrations**, including every prior type. Guard never syncs/drops application holder tables.

One Guard owns each Sequelize instance for that instance's lifetime. Use a separate connection for another Guard; a new prefix does not permit a second Guard on the same connection. Colliding registry names, extension members and physical tables are rejected before side effects. Schema-defining options and model bindings are fixed: do not reinitialize models, change schema defaults or mutate table identities after binding. The application owns and closes its Sequelize connection.

The canonical [advanced recipe](https://github.com/lotivo/sequelize-guard/blob/master/examples/advanced.mjs) executes holder isolation, inheritance/revocation, caller-transaction rollback and event suppression against the exact archive.
