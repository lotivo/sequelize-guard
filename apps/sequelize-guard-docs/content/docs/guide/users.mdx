A user receives permissions through assigned roles. You can use Guard's built-in user model, connect your application's existing user model, or assign roles to another model such as a team.

## Use the built-in user

With an initialized `guard`, create a user and assign a role:

```typescript
const user = await guard.makeUser();
await guard.allow('reader', 'read', 'article');
await user.assignRole('reader');

console.log(await user.can('read article')); // true
console.log(await user.isA('reader')); // true

await user.rmAssignedRoles(['reader']);
console.log(await user.can('read article')); // false
```

Use persisted instances of the configured model when passing a user to Guard methods. An ID alone is not a user instance or proof of identity; your application handles [authentication](/docs/guide/authorization).

## Connect an existing user model

Define your model on the same Sequelize instance before constructing Guard. Run your application and Guard [migrations](/docs/guide/db-migrations) before using this setup:

```typescript
import { DataTypes, Model } from 'sequelize';
import { SequelizeGuard } from 'sequelize-guard';

class Account extends Model<{ uid: string; email: string }> {
  declare uid: string;
  declare email: string;
}

Account.init(
  {
    uid: { type: DataTypes.STRING, primaryKey: true },
    email: { type: DataTypes.STRING, allowNull: false },
  },
  { sequelize, tableName: 'accounts', timestamps: false },
);

const guard = new SequelizeGuard(sequelize, {
  UserModel: Account,
  userPk: 'uid',
  sync: false,
});
await guard.ready;

const user = await guard.models().GuardUser.create({
  uid: 'acct-1',
  email: 'reader@example.com',
});
await user.assignRole('reader');
```

Creating through `guard.models().GuardUser` preserves your model's required TypeScript fields and exposes the added Guard methods. `makeUser()` supplies no attributes, so it cannot fill required fields such as `email`.

The model needs one supported primary key: integer, string or UUID. `userPk` accepts its attribute name or physical column name; omit it to use the model's primary key. Composite and unsupported keys are rejected before schema changes.

The [complete custom-user example](/docs/examples/basic#use-a-custom-user-with-typescript) includes migration setup and verifies that Guard rollback preserves the application user table.

## Assign roles in bulk

Give the same roles to several users in one operation:

```typescript
const alice = await guard.makeUser();
const bob = await guard.makeUser();

const result = await guard.assignRolesToUsers([alice, bob], ['reader']);
console.log(result.assigned); // 2
```

This snippet uses the built-in user model. With a custom model, create users with their required attributes as shown above.

For different roles per user, pass individual assignments:

```typescript
await guard.assignUserRoles([
  { user: alice, roles: ['reader', 'editor'] },
  { user: bob, roles: ['reader'] },
]);
```

Bulk assignment is atomic and deduplicates input. The returned `assigned` count includes new or reactivated memberships; an unchanged existing membership does not increase it.

### Read direct memberships

| Method | Result |
| --- | --- |
| `guard.getUserRoles(user)` | Plain data for active direct roles. |
| `user.roles()` | Active direct role models without junction data. |
| `user.getRoles()` | The standard Sequelize association method and query options. |
| `user.isA('editor')` | Whether the user directly holds that role. |
| `user.isAnyOf(['editor', 'reader'])` | Whether at least one listed role is directly assigned. |
| `user.isAllOf(['editor', 'reader'])` | Whether every listed role is directly assigned. |

Inherited permissions affect `can()`, but do not add parent roles to these direct membership checks.

## Give a team its own roles

Register initialized application models when constructing Guard. In this example, `Team` is your existing model and its table has already been created by application migrations:

```typescript
const guard = new SequelizeGuard(sequelize, {
  sync: false,
  roleHolders: { team: Team },
});
await guard.ready;

const team = await Team.findByPk(teamId, { rejectOnEmpty: true });
await guard.allow('reader', 'read', 'article');
await guard.assignRolesToHolder(team, ['reader']);

console.log(await guard.holderCan(team, 'read article')); // true
console.log(await guard.getHolderRoles(team)); // Plain data for direct roles

await guard.removeRolesFromHolder(team, ['reader']);
console.log(await guard.holderCan(team, 'read article')); // false
```

Run the matching Guard migration with the same `roleHolders` configuration before this startup code. Guard creates separate association tables with foreign keys for each registered model. A team and another model with the same ID do not share grants. Permissions still belong to roles.

Registration keys start with a lowercase ASCII letter and contain only lowercase ASCII letters, digits or underscores. Guard never syncs or drops application holder tables.

### Add a holder type to an existing installation

1. Create the new application's table with your own migration.
2. Call `migration.addRoleHolders()` with **only the new registrations** and the existing schema options.
3. Start the next application deployment with **all registrations**, including the old types.

For example, if teams are already registered and devices are new:

```typescript
await migration.addRoleHolders(sequelize.getQueryInterface(), sequelize, {
  ...schemaOptions,
  roleHolders: { device: Device },
});
```

Here, `migration` is imported from `sequelize-guard`, `Device` is initialized on this connection, and `schemaOptions` matches the existing installation. Repeating an existing type in this call is rejected. Future constructors, `migration.down()` and `migration.upgrade()` must use the complete set, such as `{ team: Team, device: Device }`.

## Keep model bindings stable

Create one Guard per Sequelize instance for its lifetime. A different prefix does not allow a second Guard on that same instance.

Finalize model definitions and schema routing first. Do not reinitialize models or change table identities after registration. Guard rejects conflicting registry names, helper methods and tables before applying changes. Your application owns the connection and closes it at shutdown.
